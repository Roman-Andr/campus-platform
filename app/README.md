# Кампус — клиент студента

Flutter-приложение для Android, веба, Windows, macOS и Linux (ТЗ
п. 5.1.5, 5.5.2). Основная цель среза 0 — Android 8.0 (API 26) и новее.

## Требования

- Flutter stable 3.50+ (Dart 3.14+), для Android — Android SDK
  (platform 36, build-tools, NDK из `flutter doctor`) и JDK 17+.
- Для десктопа — инструменты сборки платформы, см. `flutter doctor`; для
  Linux ещё `libsecret-1-dev` (защищённое хранилище токенов).

## Сборка на машине с 8 ГиБ RAM

Gradle, Kotlin-демон, Flutter и эмулятор делят память, поэтому профиль
сборки ограничен в `android/gradle.properties`:

- `org.gradle.jvmargs` — heap 2 ГиБ, metaspace 768 МиБ,
  code cache 256 МиБ;
- `org.gradle.workers.max` — 2;
- `kotlin.daemon.jvmargs` — heap 1 ГиБ, metaspace 512 МиБ.

Параллельные debug- и release-сборки или сборка при запущенном
эмуляторе могут не уложиться в 8 ГиБ. Порядок для машины с 7,6 ГиБ RAM:

```sh
cd app
flutter pub get --enforce-lockfile
# Сборки — последовательно, без запущенного эмулятора.
flutter build apk --debug        # app-debug.apk
flutter build apk --release      # app-release.apk
# Демоны после сборки не нужны и держат память.
cd android && ./gradlew --stop
```

APK лежат в `build/app/outputs/flutter-apk/`. `./gradlew --stop`
останавливает Gradle-демоны; Kotlin-демон завершится по своему таймауту
простоя. Если памяти всё равно не хватает, закройте браузер и IDE: swap
помогает, но не заменяет физическую RAM. Для разовой сборки с большим
heap задайте `org.gradle.jvmargs` в `~/.gradle/gradle.properties` —
пользовательский файл переопределяет проектный.

Эмулятор для такой машины — 2 ГиБ RAM и 2 ядра. AVD создаётся один
раз, а память задаётся при каждом запуске (или постоянно — в
`~/.android/avd/campus_api36.avd/config.ini`: `hw.ramSize=2048`,
`hw.cpu.ncore=2`, `vm.heapSize=256`):

```sh
echo no | avdmanager create avd -n campus_api36 \
  -k "system-images;android-36;google_apis;x86_64" --device pixel_6
emulator -avd campus_api36 -memory 2048 -cores 2 -no-snapshot-save &
adb wait-for-device
flutter run -d emulator-5554
```

Запускайте эмулятор после того, как APK собран: `flutter run` пересоберёт
только изменившееся, уже в тех же лимитах.

## Клиент API

Клиент генерируется из схемы OpenAPI сервера
([swagger_parser](https://pub.dev/packages/swagger_parser): клиент на
Dio, модели без сторонних сериализаторов) одной командой из `app/`:

```sh
tool/generate_api.sh            # после изменения API сервера
tool/generate_api.sh --check    # схема и клиент актуальны?
```

Команда берёт схему из приложения FastAPI (`backend/`, нужен
[uv](https://docs.astral.sh/uv/)), а не с запущенного сервера, сохраняет
её в `openapi/openapi.json` (`tool/export_openapi.py` переписывает
`anyOf: [T, null]` FastAPI в `T | null`, который понимает генератор) и
генерирует `lib/src/core/api/generated/` (настройки —
`swagger_parser.yaml`). Сгенерированный код руками не правится.
CI запускает `tool/generate_api.sh --check` при изменениях клиента или
сервера, чтобы схема и клиент оставались согласованы. Если операция
объявляет несколько успешных статусов с одной моделью (например, `200` и
`201`), `swagger_parser` в режиме `first_success` оставляет только низший.
`tool/accept_success_statuses.py` детерминированно добавляет остальные
такие статусы в `validateStatus` сгенерированного клиента; скрипт входит
в генерацию и в проверку `--check`.

Запросы идут через общий `Dio` (`apiDioProvider`, клиент —
`campusApiProvider`), его перехватчики (`lib/src/core/api/`):

- добавляют `X-Client-Platform`, `X-Client-Version` (из `pubspec.yaml`)
  и `Accept-Language` к каждому запросу — в генерированных методах этих
  параметров нет;
- дают каждому изменяющему запросу (POST, PUT, PATCH, DELETE)
  `Idempotency-Key` — UUIDv7. Ключ хранится в параметрах запроса, поэтому
  повтор после обрыва связи или тайм-аута
  ([dio_smart_retry](https://pub.dev/packages/dio_smart_retry)) идёт с
  тем же ключом и сервер выполняет операцию один раз. Ключ, переданный
  вызывающим кодом, сохраняется;
- отмечают офлайн-состояние (полоса «Нет подключения к сети» над
  экраном; источник — также
  [connectivity_plus](https://pub.dev/packages/connectivity_plus)) и
  ответ `426 client_update_required` — после него доступен только экран
  «Требуется обновление» со ссылкой на загрузку.

Ошибки запросов разбираются в `ApiFailure.from(error)`: `NetworkFailure`,
`ProblemFailure` (Problem Details с `code` и `fieldErrors`),
`UpdateRequiredFailure`, `UnexpectedFailure`. Пользователю показывается
текст из ARB (`apiFailureMessage`, виджет `ApiErrorView`) — не `title` и
`detail` сервера и без технических подробностей; новые коды ошибок
сервера не ломают старый клиент.

## Realtime (Centrifugo)

`core/realtime/` — клиент Centrifugo для событий личных каналов
(`user#<uuid>`) и чатов (`chat:<uuid>`), других имён сервер не выдаёт.
Подключение ленивое: клиент `centrifuge` открывает WebSocket при первой
подписке и отключает его при выходе. На каждый канал создаётся одна
подписка SDK, сколько бы экранов её ни слушали; последний слушатель
отписывается.

Токены подключения и подписки выдаёт API (`/realtime/connection-token`,
`/realtime/subscription-token`) через `RealtimeTokens`. Токен кешируется
до истечения с `CAMPUS_REALTIME_TOKEN_MARGIN`; одновременные запросы SDK
ждут один запрос, а повторы после обрыва связи используют общий
`Idempotency-Key`. Выход и отзыв сессии очищают кеш, поэтому новый
пользователь не получает токены предыдущего.

Переподключение с экспоненциальной задержкой (`min`/`max` выше) и
обновление токенов делает SDK. Подписки создаются с `recoverable` и
`positioned`: при обрыве клиент восстанавливает пропущенные публикации с
сохранённой позиции. Обработчик `getState` сначала спрашивает
`/realtime/recover` с `since` и отдаёт полученные публикации без повторов
по `offset`. Если история исчерпана (`409 realtime_history_lost`),
состояние канала перезагружается через API (обратный вызов `reload`),
затем подписка продолжается с текущей позиции; экран не показывает
неполную историю как полную. Повторные публикации отбрасываются по
`offset`, при смене `epoch` нумерация начинается заново.

Жизненный цикл: при уходе в фон клиент отключается, при возврате
помечает данные устаревшими, перезагружает состояние всех каналов через
API и переподключается — до завершения загрузки устаревшее состояние не
выдаётся за текущее. Выход или отзыв сессии (`401` при обновлении
токена) останавливает события и очищает подписки. Глобальная полоса
`RealtimeStatusBanner` показывает переподключение, загрузку и ошибки
(RU/EN ARB); при офлайн-устройстве она скрыта, потому что об этом уже
сообщает полоса сети. `RealtimeStatusView` — состояние канала и время
последнего события в поясе города через `formatCityTime` (#44).

Тесты: `test/core/realtime/` — токены, подписка и дедупликация,
переподключение после потери сети, повтор запроса токена, запрет канала,
временная ошибка, исчерпанная история, очистка при выходе, фон/возврат;
widget-тесты проверяют полосы, ошибки и время города.

## Вход

Вход по коду из письма (ТЗ п. 5.1.1, модуль 1; сервер — раздел «Вход по
коду из письма» в `backend/README.md`): экраны `features/auth/` — почта,
код с таймером повторной отправки, имя и фамилия при первом входе. Без
сессии доступны только эти экраны (`AppRoutes.signIn…`), с сессией они
недоступны.

Сессия — `core/auth/`:

- refresh-токен и идентификатор устройства (UUIDv7, один на установку,
  сохраняется после выхода) лежат в защищённом хранилище
  ([flutter_secure_storage](https://pub.dev/packages/flutter_secure_storage):
  на Android шифруются ключом Android Keystore). Access-токен хранится
  только в памяти. Автобэкап Android выключен: ключ Keystore в бэкап не
  попадает, и восстановленные данные не расшифровать;
- перехватчик [fresh_dio](https://pub.dev/packages/fresh_dio) добавляет
  `Authorization` к операциям, у которых в схеме OpenAPI есть
  `security` (у сгенерированных методов — `extra['openapi.security']`),
  обновляет access-токен заранее (за `CAMPUS_TOKEN_REFRESH_MARGIN`) или
  после ответа 401 и повторяет запрос. Запросы ждут идущее обновление,
  поэтому сколько угодно параллельных запросов с истёкшим токеном
  вызывают одно обновление;
- ответ 401 на обновление (сессия отозвана, повтор старого
  refresh-токена) завершает сессию: `authStatusProvider` становится
  `unauthenticated`, и приложение переходит на экран входа. Сетевые
  ошибки сессию не завершают;
- выход (`AuthService.signOut`, пункт в настройках) отзывает сессию на
  сервере и удаляет токены, даже если сервер недоступен.

Токены не пишутся в журналы: в приложении нет журналирования запросов, а
`toString()` токенов и черновика входа их не содержит (тест
`test/core/auth/auth_session_test.dart`).

Ответ 429 повторяется автоматически, только если `Retry-After` не больше
паузы перед повтором; иначе пользователь видит, сколько ждать, а таймер
повторной отправки кода продлевается до этого срока.

### Согласия и документы

При регистрации пользователь открывает текущие тексты правил, политики
и согласия на обработку ПДн и отмечает обязательный флажок. Отдельный
необязательный флажок даёт согласие на трансграничную передачу; версии
передаются серверу вместе с именем и кодом.

Ответ `403 consent_required` на защищённый запрос скрывает текущий экран
до принятия документов. Исходный экран и его состояние сохраняются;
после принятия ожидающие запросы повторяются с прежними телами и ключами
идемпотентности. Выход доступен и завершает ожидающие запросы без повтора.
При смене обязательных версий во время принятия требуется новый флажок.

Настройки → «Согласия и документы»: текущие тексты на языке интерфейса,
выдача и отзыв согласия на трансграничную передачу. Перед отзывом диалог
перечисляет последствия для push, Telegram-бота и ИИ-функций; состояние
после изменения загружается с сервера.

### Интеграционный тест

`integration_test/sign_in_test.dart` проходит регистрацию, заполнение
профиля, обновление токена и выход против запущенного стенда: API,
воркер и Mailpit, из
которого тест берёт код. Пример с эмулятором Android и стендом из
`infra/` (README там же): порты стенда пробрасываются в эмулятор через
adb, поэтому адреса — `127.0.0.1` (`10.0.2.2` тоже подойдёт, если у
эмулятора есть сеть):

```sh
adb reverse tcp:8000 tcp:8000 && adb reverse tcp:8025 tcp:8025
flutter test integration_test -d emulator-5554 \
  --dart-define=CAMPUS_API_URL=http://127.0.0.1:8000 \
  --dart-define=CAMPUS_TEST_MAILPIT_URL=http://127.0.0.1:8025
```

После неверного кода тест ждёт доступности поля и явно восстанавливает
фокус перед следующим вводом: отключение поля на время запроса закрывает
IME, но на устройстве не сбрасывает кеш `focusedEditable` тестового
binding. Один `enterText` в этом случае теряет ввод. Управляемый сценарий
`test/features/auth/cold_sign_in_test.dart` воспроизводит потерю ввода
после задержанного 401 и проверяет исправление без эмулятора. Сквозной
тест также проверяет ответы `sign_in_code_invalid` (401) и
`registration_required` (422), выводя только статус и код ошибки.

Адрес регистрируется в домене `CAMPUS_TEST_EMAIL_DOMAIN` (по умолчанию
`edu.hse.ru` из начальных данных); справочники загружает `campus-seed`.

## Профиль

После первого входа, пока профиль не заполнен, доступен только экран
`AppRoutes.profileSetup` (ТЗ п. 5.1.1, модуль 2, п. 1; сервер — раздел
«Профиль» в `backend/README.md`): город-кампус, затем общежитие этого
города или «Не живу в общежитии», факультет этого города и курс (у
сотрудников курса нет). Списки — из справочников сервера на языке
интерфейса; при смене города выбор общежития и факультета сбрасывается.
Отсюда можно только выйти из аккаунта.

Профиль (`myProfileProvider`, `features/profile/`) загружается с сервера
(`GET /me`) после каждого входа и запуска, поэтому на другом устройстве он
тот же. Пока профиль загружается или не загрузился, пользователь остаётся
на текущем экране. Свой профиль — `AppRoutes.profile` (кнопка на
главном экране), изменение — `AppRoutes.profileEdit`.

### Адреса почты

Профиль → «Адреса почты» (`AppRoutes.profileEmails`, `features/account_emails/`):
корпоративные и резервный личный адрес. Новый адрес появляется в списке
только после кода, отправленного на него; резервный адрес заменяется
новым и нужен только для входа и уведомлений о безопасности — прав он не
даёт. После добавления или удаления корпоративного адреса профиль
перезагружается, поэтому метка типа аккаунта меняется без перезапуска
приложения. Последний корпоративный адрес удалить нельзя. Ошибки сервера
(занятый адрес, неподходящий домен, лимит частоты) показываются у поля
ввода; тексты — RU/EN ARB.

## Личные чаты

Личные диалоги (`features/chat/`) открываются иконкой «Мои диалоги» в
профиле, пунктом главного меню и кнопкой «Написать сообщение» у автора
объявления.
Диалог по объявлению хранит ссылку на него; повторное открытие возвращает
существующий диалог. Список и история загружаются с сервера, последний
снимок открывается без сети. Границы доступа проверяет сервер: чужой
диалог отвечает `404 chat_not_found`, а выпускник получает
`403 chat_forbidden` только при создании нового — в существующем он
пишет как обычно, и клиент не блокирует это по типу аккаунта.

История сортируется по серверному `sequence`, а не по времени устройства.
Собственные ещё не доставленные сообщения показываются отдельно:
«Отправляется…», «Ждёт отправки» или «Не отправлено» с кнопкой повтора;
ошибка никогда не выглядит как доставленное сообщение. Время — в поясе
города профиля по механизму `core/time/city_time.dart` (issue #44).

Ответ на сообщение показывает цитату с автором и видимым текстом. Правка
и удаление доступны только у собственных доставленных сообщений; меню
чужих сообщений содержит только ответ. Изменённое сообщение помечается
«Изменено», удалённое исчезает из истории. Перед удалением показывается
подтверждение: текст пропадает из интерфейса, но скрытая ревизия остаётся
на сервере для жалоб. Ответ сервера `403`/`404` не удаляет и не меняет
строку локально, а показывается рядом с диалогом. Правка и удаление
повторяются с тем же `Idempotency-Key`, поэтому повтор после потерянного
ответа не применяет операцию дважды.

Цитата — снимок видимого текста, а не ссылка на скрытую ревизию. Правка
цитируемого сообщения обновляет снимок в истории и в ещё не отправленной
очереди, удаление заменяет текст цитаты на «Сообщение удалено». При этом
`reply_to_id` в очереди не меняется: повтор с тем же `Idempotency-Key`
отправляет те же байты. Если выбранная для ответа цитата исчезла до
отправки, форма не отправляет устаревшую ссылку и просит выбрать другую.

Фото прикрепляются к сообщению только после серверной обработки. Во время
загрузки и обработки показывается прогресс/ожидание, отклонённое фото
помечается причиной и блокирует отправку до удаления или повтора; кнопка
отправки не отправляет неготовые id. Подписанные ссылки на фото живут
несколько минут: экран сам перезапрашивает их до истечения и не хранит в
БД. Если обработка не завершилась за `CAMPUS_PHOTO_PROCESSING_TIMEOUT`,
слот становится ошибочным, а не «готовым».

### Очередь отправки

Исходящее сообщение сначала попадает в таблицу `chat_outbox` Drift:
UUIDv7 сообщения (`client_id`) и UUIDv7 `Idempotency-Key` создаются один
раз и повторяются при каждом запросе, поэтому потерянный ответ после
успешной записи на сервере не создаёт второе сообщение. Отправка идёт
последовательно в порядке локального создания: сообщение того же диалога
не обгоняет предыдущее, даже если предыдущее ждёт повтора. Сетевые и
временные ошибки оставляют строку в очереди и повторяются по backoff,
после восстановления сети и после перезапуска процесса;
окончательный отказ (`409`, `403`, `404`) помечает строку «Не отправлено»
и не удаляет её без действия пользователя: рядом с «Повторить» есть
«Удалить», после которого очередь этого диалога продолжается. Успешный
ответ удаляет строку и кэширует серверное сообщение в одной транзакции.

Очередь запускается в `main` для всей сессии (`startChatQueueRuntime`), а
не только при открытом экране чата: сохранённые сообщения уходят после
перезапуска, а выход очищает диалоги, историю и очередь. Все таблицы
разделены владельцем — локальным идентификатором сессии, поэтому данные
прежнего аккаунта не видны новому.

Realtime-канал `chat:<uuid>` служит только сигналом: публикация несёт
`action`, `message_id`, `sequence` и `version`, но не текст. На `created`
и `edited` клиент точечно запрашивает это сообщение по `sequence`
(восходящая страница после `sequence - 1`), на `deleted` сразу удаляет
строку и цитаты. Правка и удаление не получают новый `sequence`, поэтому
старый алгоритм «догрузить после последнего sequence» их бы пропустил.
Пропущенная история, разрыв соединения, возврат из фона и исчерпанная
история Centrifugo вызывают сверку загруженного окна через API: оно
разбивается на непрерывные кластеры `sequence`, чтобы поисковый переход
не заставлял перечитывать весь чат. Событие, пришедшее во время запроса,
запускает ещё один проход, а не теряется. Если сверка после события всё
же не удалась, история остаётся на экране, показывает предупреждение и
кнопку повтора, а не молча пропускает сообщение.

Все ответы истории проходят через монотонную запись Drift: сообщение с
меньшей `version` не заменяет более новую правку, а `chat_message_tombstones` не даёт поздней странице воскресить удалённое сообщение.
Запоздалый ответ точечной проверки не считается доказательством удаления:
если его `version` меньше локальной, строка остаётся. Поэтому гонка
«страница/поиск/сверка против правки или удаления» не возвращает старый
текст ни в БД, ни в поиск, ни в цитаты, ни на экран.

Тесты: `flutter test --concurrency=1 test/features/chat` — сохранение
очереди после перезапуска без сети, повтор с прежними UUID и
`Idempotency-Key` после потерянного ответа, порядок, восстановление
после переподключения, изоляция аккаунтов, выход во время отправки,
мультистраничная догрузка истории, ожидающие/ошибочные сообщения и
локализованные ошибки; правка без нового `sequence`, пропущенные правки
и удаления после перезапуска, цитаты и их обновление, отказ `403`,
удаление, гонки с запоздалыми страницами и точечными ответами, фото
(`ready`/`rejected`/таймаут/повтор), лимиты и смена аккаунта во время
загрузки фото.

## Локальная БД (Drift)

SQLite через Drift (`lib/src/core/database/`); в вебе — WebAssembly
(`web/sqlite3.wasm`, `web/drift_worker.js`; после обновления `drift` или
`sqlite3` — `tool/update_drift_web_assets.sh`).

Изменение схемы:

1. Изменить таблицы и увеличить `AppDatabase.schemaVersion`.
2. `dart run build_runner build`
3. `dart run drift_dev make-migrations` — сохраняет схему новой версии в
   `drift_schemas/`, генерирует `app_database.steps.dart` и тестовые
   схемы.
4. Описать шаг в `AppDatabase.migration` (`onUpgrade: stepByStep(...)`).
5. `flutter test test/drift` — проверяет, что новая установка создаёт
   выгруженную схему и что каждая версия обновляется до каждой
   следующей.

## «Отдам»

Главная страница — лента объявлений с областью (город, факультет,
общежитие), обновлением жестом и подгрузкой следующей страницы. Последний
снимок каждой области хранится в Drift (схема v2). При сетевой ошибке
запуска показываются сохранённые объявления и общая полоса офлайн-состояния.
Кэш привязан к случайному идентификатору сессии в secure storage:
ротация токена его сохраняет, выход удаляет привязку. Токены в SQLite
не записываются.

Из ленты доступны карточка с автором, бронь и создание объявления.
Перед публикацией обязательна категория из `/listings/categories`.
Справочник загружается с обработкой ошибок и повтором; публикация отправляет
`category_id` и `draft=false`. «Мои» использует `/listings/mine`.
Черновик без срока действия и статусы «Завершено», «Скрыто», «Неявка»
отображаются отдельно. Старые снимки кэша без новых nullable-полей
читаются с пустыми значениями этих полей.
«Мои объявления и брони» показывает свои объявления (включая архивные),
входящие заявки в карточке автора с принятием/отклонением и собственные
брони со статусами. Права и переходы проверяет сервер; POST-запросы
используют общий перехватчик Idempotency-Key. Тексты ошибок — RU/EN ARB.

Сквозной Android-тест использует настоящий API, PostgreSQL и Redis,
аутентифицирует два отдельных аккаунта и проходит публикацию → бронь →
принятие → просмотр принятой брони вторым пользователем. Запуск из
`backend/` с запущенным `emulator-5554` и настроенным rootless Podman:

```sh
CAMPUS_RUN_GIVEAWAY_CLIENT=1 uv run pytest tests/test_giveaway_client.py -s
```

Тест сам поднимает временную БД и HTTP-сервер, заполняет профили и
передаёт данные тестовых сессий через временный файл вне репозитория.
Обычный `uv run pytest` пропускает Android-проверку. После проверки:
`adb emu kill`, затем `cd app/android && ./gradlew --stop`.

Мероприятие проверяется так же: организатор публикует встречу с одним
местом, первый участник записывается, второй видит «мест нет» и встаёт
в очередь:

```sh
CAMPUS_RUN_EVENT_CLIENT=1 uv run pytest tests/test_event_client.py -s
```

## Совместные закупки

Создание закупки (`/purchase/new`) задаёт цену за единицу, минимальный и
максимальный объём и срок сбора; сумма всегда равна цене за единицу на
число единиц. Карточка показывает этап, набранный объём из минимума и
максимума, цену и срок, а участник вводит долю с проверкой свободного
объёма до отправки. Пока идёт сбор, долю можно изменить или выйти; после
фиксации состава кнопка выхода заменяется запросом организатору, который
видит состав с суммами и разрешает или отклоняет запросы. Тексты — в RU
и EN ARB; расчёты долей проверяются unit- и widget-тестами.

Сквозной Android-тест двумя пользователями (публикация → доля 2 →
изменение на 3 → пересчитанная сумма у организатора) из `backend/`:

```sh
CAMPUS_RUN_PURCHASE_CLIENT=1 uv run pytest tests/test_purchase_client.py -s
```

## Фото

Общий загрузчик — `core/photos/photo_upload.dart`: `PhotoPicker` (пакет
`image_picker`: камера и галерея на Android, диалог файла в вебе и на
десктопе), `PhotoUploader` (подписанная POST-форма S3 с прогрессом →
`/files/{id}/complete` → опрос статуса до `ready` или `rejected`) и
параметры `PhotoConfig`. Повтор после сбоя начинает загрузку заново;
брошенные загрузки сервер удаляет сам.

В форме объявления (`ListingPhotosField`) — до 10 фото, проверка размера
до отправки, состояния «Загружается», «Обрабатывается», «Отклонено» с
причиной, порядок (перетаскивание или кнопка «левее») и удаление.
Публикация ждёт окончания загрузок; отклонённые и неудачные фото не
мешают: к объявлению привязываются только готовые, в выбранном порядке.
Карточка показывает галерею, лента — превью первого фото. Ссылки на фото
подписаны и короткоживущие, поэтому кэш изображений
(`cached_network_image`) хранит их по id файла, а список ссылок
обновляется до истечения срока.

Сквозной Android-тест фото (выбор → загрузка в RustFS → обработка →
публикация → фото на карточке у другого пользователя), из `backend/`:

```sh
CAMPUS_RUN_PHOTO_CLIENT=1 uv run pytest tests/test_photo_client.py -s
```

## Время города

`core/time/city_time.dart` загружает встроенную базу IANA пакета `timezone`
при первом обращении. `cityTimeToUtc` переводит календарные поля города
в UTC независимо от устройства. `formatCityTime` форматирует момент
в поясе города; если смещение устройства в этот момент отличается,
добавляет локализованную пометку города и UTC-смещения.

`CityDateTimePicker` принимает UTC-значение, IANA-пояс, локализованное имя
города, границы календарных дат и `onChanged(DateTime)` с UTC-результатом.
Оба диалога редактируют календарные поля города. Несуществующее местное
время при переходе DST отклоняется с сообщением RU/EN; для повторяющегося
времени выбирается первое наступление. Форматирование использует `intl`
после загрузки делегатов локализации приложения.
