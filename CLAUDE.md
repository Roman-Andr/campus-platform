# Кампус — сервис взаимодействия студентов

Курсовой проект: закрытое сообщество студентов вуза — обмен вещами и
навыками, мероприятия, совместные закупки, взаимопомощь.

- Требования — ТЗ: `docs/paperwork/ТЗ/` (функции — п. 5.1.1, этапы — §8,
  приёмка — §9, параметры по умолчанию — Приложение 4).
- Видение и принятые решения — `docs/vision.md`.
- Стек — ТЗ п. 5.5.2: Python 3.12+, FastAPI, SQLAlchemy 2, Alembic, Taskiq,
  PostgreSQL 18 + pgvector, Redis, Centrifugo, RustFS; клиент — Flutter
  (Riverpod, Drift, `go_router`); веб-панель — React + react-admin.
  Готовые библиотеки предпочтительнее собственных реализаций.

## Структура репозитория

- `backend/` — API, воркер и планировщик
- `app/` — клиент студента на Flutter (Android, веб, десктоп, Mini App)
- `admin/` — веб-панель администратора
- `infra/` — Docker Compose, Caddy, резервное копирование, мониторинг
- `docs/` — документы проекта и ЕСПД (Typst)

## План работ

- Дорожная карта — закреплённая issue #1. Иерархия через под-задачи:
  Roadmap → эпик среза → (эпик модуля) → фича.
- Срез = milestone с датой из ТЗ §8. Конец среза — тег `vX.Y.0` и
  GitHub Release со сборками.
- Зависимости — только связью «blocked by», не текстом в описании.
- Метки: `epic`, `in-progress`, `stub`, `spec`, `bug`, `area:*` (слой),
  `mod:NN-*` (модуль п. 5.1.1 — по ним проверяется приёмка).
- `stub` — заготовка: контекст и объём есть, критериев приёмки нет.
  Детализируется перед стартом своего среза (критерии приёмки, при
  необходимости разбиение и уточнение зависимостей), после чего метка
  снимается. В работу заготовки не берутся.

## Статусы issue

| Статус      | Признак                                                  |
|-------------|----------------------------------------------------------|
| Todo        | открыта, без метки `in-progress`                         |
| In progress | метка `in-progress` + комментарий «взял <агент>, ветка …» |
| In review   | открыт PR с `Closes #N`                                  |
| Done        | закрыта мержем PR; метку `in-progress` снимает workflow  |

## Цикл работы над issue

1. Выбрать фичу текущего среза — открытую, без блокеров и не взятую:
   ```sh
   gh issue list --milestone "<срез>" \
     --search "-is:blocked -label:in-progress -label:epic -label:stub"
   ```
2. Взять её:
   ```sh
   gh issue edit N --add-label in-progress
   gh issue comment N --body "Взял: <имя агента Herdr>, ветка <ветка>"
   ```
3. Работать в отдельном worktree: ветка `<type>/N-short-slug` от
   `origin/main`, где `<type>` — тип Conventional Commits:
   ```sh
   git worktree add ../campus-wt/N -b feat/N-short-slug origin/main
   ```
4. Открыть PR: `gh pr create`. При squash-мерже заголовок PR становится
   заголовком коммита, описание — его телом.
   - Заголовок — Conventional Commits на английском, повелительное
     наклонение, до 50 символов: `feat: book a giveaway item`.
   - Описание — на английском, как тело коммита: что и зачем, перенос
     строк до 72 символов, в конце `Closes #N`. Как проверено — отдельным
     комментарием к PR.
5. Агент-исполнитель не мержит свой PR: он сообщает ссылку
   координатору — главной сессии Claude в Herdr. Координатор проверяет
   CI и критерии приёмки, делает ревью и squash-мерж, после мержа
   удаляет worktree и назначает следующую задачу.

## Правила

- Одна issue — один PR. Не помещается — разбить issue на под-задачи.
- Работа, найденная по ходу, — новая issue в нужном эпике
  (`gh issue create --parent <эпик> --milestone "<срез>"`), а не
  расширение текущего PR.
- Реализация расходится с ТЗ — issue с меткой `spec`; ТЗ правится
  отдельным PR.
- Не трогать чужие ветки, worktree и issues с меткой `in-progress`.
- Не пушить в `main` напрямую.
- Без строк `Co-Authored-By` и подписей Claude Code в коммитах и PR.
- Issues и комментарии к ним — на русском; код, комментарии в коде,
  коммиты и PR — на английском.

## Структура issue

Фича (шаблон `.github/ISSUE_TEMPLATE/feature.yml`), разделы:
`### Контекст` (пункты ТЗ, например «п. 5.1.1, модуль 4, пункт 8»),
`### Что сделать`, `### Не входит`, `### Критерии приёмки` (проверяемые
утверждения списком `- [ ]`; из них получаются кейсы ПМИ).
Родитель — эпик, milestone — срез, метки `area:*` и `mod:*`.

## Definition of Done для фичи

Выполняются пункты, применимые к фиче:
- Права проверяются на сервере (роль, область, права на объект); тест на
  каждую затронутую ячейку матрицы «роль × действие».
- Схема БД меняется только миграцией Alembic.
- Тесты на настоящем PostgreSQL: каждый разрешённый и запрещённый переход
  статуса; инварианты согласованности — параллельными запросами; события
  по сроку — с управляемым временем; на клиенте — unit и widget.
- Изменяющие запросы принимают `Idempotency-Key`; ошибки — в формате
  Problem Details.
- Схема OpenAPI и сгенерированный клиент обновлены.
- Тексты интерфейса — в файлах локализации RU и EN.
- Числовые параметры — в конфигурации (ТЗ, Приложение 4), не в коде.
- CI зелёный, покрытие доменных модулей не ниже 80 %.
- Критерии приёмки из issue выполнены.
